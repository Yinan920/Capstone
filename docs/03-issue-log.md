# 3. Issue Diagnosis, Research, Resolution & Sharing

Sixteen issues that materially changed the system, in the order they were met. Each follows the same template: **what happened → environment → reproduce → diagnosis → research → resolution → verification**.

Three of them (8, 9, 14) were only exposed by running the real Claude models at real dataset sizes; four (10, 11, 12, 14) were caught by browser end-to-end tests that unit tests could not have caught; one (13) came from instructor feedback on the first presentation.

**About the research column.** Where a fix is documented in an official source, that source is cited — it is the canonical reference for the behaviour described. Development used Claude (via Claude Code) as a pair-programming assistant; commits that were produced that way carry a `Co-Authored-By` trailer in the git history, so the record is auditable.

### Issue 1 — npm ci fails inside the Docker build, though npm install works locally

**What happened.** The frontend build stage of the production image failed immediately. *Expected:* the same dependency install that succeeds on the development machine. *Actual:* `npm ci` aborted, reporting the lockfile was out of sync with `package.json`.

**Environment.** macOS host, local npm 11; image stage `node:22-slim`, which ships npm 10. Repository at the point of writing the first `Dockerfile`.

**Reproduce.** `docker build -t sellersense:local .` with a `package-lock.json` last written by npm 11.

**Diagnosis.** `npm ci` deliberately refuses a lockfile it considers inconsistent — that strictness is the entire point of the command. The lockfile had been regenerated by a newer npm than the one inside the image, and the two versions disagreed about its shape. The host and the image had drifted.

**Research.** npm CLI documentation for `ci` (it errors rather than reconciling, unlike `install`); the npm lockfile version history describing format changes between major npm releases.

**Resolution.** Regenerate the lockfile **with the image's own npm**, rather than downgrading the Dockerfile to `npm install`:

```bash
docker run --rm -v "$PWD/frontend":/fe -w /fe node:22-slim npm install --package-lock-only
```

The tempting alternative — switching the Dockerfile to `npm install` — would have made the build succeed while silently giving up reproducible builds. Rejected.

**Verification.** `docker build` completes; the image builds identically on a clean machine. The Dockerfile still uses `npm ci --ignore-scripts`.

### Issue 2 — The container deploys successfully, then cannot reach the database

**What happened.** `gcloud run deploy` reported success. *Expected:* a working service. *Actual:* every request timed out, and the logs contained nothing but a connection timeout — no permission error, no stack trace.

**Environment.** First deployment to Cloud Run, us-central1, with Cloud SQL attached and secrets configured, using the **default compute service account**.

**Reproduce.** Deploy without `--service-account`, with `--add-cloudsql-instances` and `--set-secrets` set, then request any endpoint that touches the database.

**Diagnosis.** The default compute service account lacks `roles/cloudsql.client` and `roles/secretmanager.secretAccessor`. The failure mode is nasty precisely because it is quiet: the *deploy* is a control-plane operation that succeeds regardless, and the identity problem only surfaces at runtime as a connection that never establishes.

**Research.** Cloud Run documentation on service identity and connecting to Cloud SQL; Cloud SQL documentation for the connector's IAM requirements; Secret Manager access-control documentation.

**Resolution.** Create a dedicated runtime service account with exactly the two roles it needs, and deploy with it:

```bash
gcloud iam service-accounts create sellersense-run
gcloud projects add-iam-policy-binding sellersense-yinan920 \
  --member="serviceAccount:sellersense-run@sellersense-yinan920.iam.gserviceaccount.com" \
  --role="roles/cloudsql.client"
gcloud projects add-iam-policy-binding sellersense-yinan920 \
  --member="serviceAccount:sellersense-run@sellersense-yinan920.iam.gserviceaccount.com" \
  --role="roles/secretmanager.secretAccessor"
gcloud run deploy sellersense --service-account sellersense-run@…
```

This is both the fix and the least-privilege posture — the service account can reach the database and read secrets, and can do nothing else.

**Verification.** `/api/health` returns `"database":"up"`; the full smoke test passes against the deployed URL. Playbook: [§1.4 I-3](01-production-support.md#i-3--a-new-revision-will-not-start-secrets--iam).

### Issue 3 — The analysis pipeline stalls after the upload returns 201

**What happened.** On Cloud Run, uploads returned `201` instantly and the job then sat at low progress indefinitely. *Expected:* the same behaviour as locally, where the pipeline finishes in seconds. *Actual:* the job never advanced.

**Environment.** Cloud Run with default (request-based) billing; the pipeline runs as a FastAPI `BackgroundTask` — that is, **after** the response has been sent.

**Reproduce.** Deploy without `--no-cpu-throttling`, upload a CSV, poll `GET /api/jobs/{id}`.

**Diagnosis.** Under request-based billing Cloud Run throttles CPU to near zero between requests. Work scheduled to run after the response therefore gets almost no CPU. This is not a bug in the application; it is the documented economics of the platform meeting a design that does work outside the request.

**Research.** Cloud Run documentation on CPU allocation (request-based vs instance-based billing) and on background activity; Starlette/FastAPI documentation on `BackgroundTasks` executing after the response.

**Resolution.** Deploy with instance-based billing:

```bash
gcloud run deploy sellersense --no-cpu-throttling …
```

Two consequences are recorded rather than hidden:

- Instance-based billing does not qualify for the request-based free tier. At demo traffic the realistic cost is ~15 minutes of instance lifetime per session — negligible, but not free.
- The flag guarantees CPU **while the instance lives**, not that it lives. On scale-down Cloud Run sends SIGTERM with a ~10 s grace period, so a mid-flight analysis can still be killed. Mitigations: job state is persisted, so a stuck job is detectable and the upload is repeatable; and the pipeline sits behind a `JobRunner` abstraction whose upgrade path is Cloud Tasks or a Cloud Run Job per analysis.

**Verification.** Uploads reach `done` on the deployed service; measured at 19–21 s warm for 50 reviews with real Claude ([benchmarks.md](benchmarks.md#2-deployed-50-reviews-real-claude)). Playbook: [§1.4 I-5](01-production-support.md#i-5--an-analysis-job-is-stuck-in-running).

### Issue 4 — Concurrent instances would race Alembic migrations

**What happened.** A pre-emptive fix rather than an outage. The obvious pattern — run `alembic upgrade head` in the container's start command — is unsafe on Cloud Run.

**Environment.** Cloud Run with `--max-instances 2` and autoscaling; a single Cloud SQL database.

**Reproduce (in principle).** Put migrations in the entrypoint and let two instances start simultaneously after a deploy; both attempt to acquire the same DDL locks.

**Diagnosis.** Cloud Run starts instances concurrently and without ordering. Alembic assumes one migrating process; several racing each other against one database produces lock contention and, at worst, a partially applied schema.

**Research.** Cloud Run documentation on container lifecycle and startup concurrency; Alembic documentation on running migrations as a discrete operational step.

**Resolution.** Migrations run as a **one-off Cloud Run Job** using the same image with the command swapped, executed exactly once per deploy; the service's own start command never migrates:

```bash
gcloud run jobs execute sellersense-migrate --region us-central1 --wait   # alembic upgrade head
gcloud run jobs execute sellersense-seed    --region us-central1 --wait   # python -m scripts.seed
```

**Verification.** Migration jobs complete with a single execution log; the service scales freely afterwards. `alembic current` reports `0001 (head)` against the production database.

### Issue 5 — Switching to real Claude would have crashed the image

**What happened.** The project's central claim is that swapping AI providers is *configuration, not code*. Testing that claim revealed it was not yet true.

**Environment.** Production image built with `pip install .`; `anthropic` declared as an **optional** extra in `pyproject.toml`.

**Reproduce.** Build the image with `pip install .`, then set `LLM_PROVIDER=anthropic`. The provider factory imports `app.integrations.llm.anthropic`, which imports the `anthropic` SDK — `ModuleNotFoundError` at the first analysis.

**Diagnosis.** Optional extras are not installed by a plain `pip install .`. The adapter interface was correct; the *packaging* did not match the promise made about it.

**Research.** Python packaging documentation on optional dependencies and extras syntax (`.[extra]`).

**Resolution.** The Dockerfile installs the extra explicitly:

```dockerfile
RUN pip install --no-cache-dir ".[anthropic]"
```

`sentence-transformers` is deliberately *not* installed — it would add roughly 2 GB for an embedding provider the cloud deployment does not use.

**Verification.** The real path was then run end-to-end on the deployed service: 50 reviews analysed with Haiku 4.5 + Sonnet 5, producing three complaint themes where the keyword heuristic found two. Switching providers today takes one `gcloud run services update` and no rebuild.

### Issue 6 — pgvector might not be creatable on managed Postgres

**What happened.** A risk checked before it could become an incident: the schema depends on `CREATE EXTENSION vector`, and managed Postgres services restrict which extensions a non-superuser may create.

**Environment.** Cloud SQL for PostgreSQL 16; the first Alembic migration begins with `CREATE EXTENSION IF NOT EXISTS vector`.

**Reproduce.** Run the migration as a user without the required privilege on a provider whose allow-list excludes `vector`.

**Diagnosis.** Cloud SQL's default user carries `cloudsqlsuperuser`, which may create extensions that appear on the provider's allow-list — and `vector` is on it. So the migration works; it was verified rather than assumed.

**Research.** Cloud SQL documentation on PostgreSQL extensions and the `cloudsqlsuperuser` role; pgvector installation documentation.

**Resolution.** No code change. The documented fallback for a stricter provider is a single `CREATE EXTENSION vector` executed by an admin through the Cloud SQL Auth Proxy before the first migration.

**Verification.** The migration job created the extension and all 9 tables on the first run; `\dx` lists `vector` in the production database.

### Issue 7 — The public URL could not be shortened

**What happened.** The Cloud Run URL is long and contains the project number, which is awkward to read aloud in a demo. *Expected:* rename the service to shorten it. *Actual:* the hostname is not renameable.

**Environment.** Cloud Run service in project `sellersense-yinan920`; no custom domain owned.

**Diagnosis.** A `*.run.app` hostname embeds the project *number*, so it cannot be shortened — only a domain placed in front of it can. Firebase Hosting's free `*.web.app` subdomain solves this, but has two hard constraints that must be known before starting:

1. A Hosting site can only rewrite to a Cloud Run service in the **same GCP project** — so Firebase had to be added to the existing project with `firebase projects:addfirebase`, not created as a separate Firebase project.
2. Site IDs are **globally unique**. `sellersense` was already taken; hence `sellersense-ai`.

Cloud Run rewrites also require the **Blaze** billing plan.

**Research.** Firebase Hosting documentation on serverless rewrites to Cloud Run and on site IDs; the `firebase projects:addfirebase` CLI reference.

**Resolution.**

```bash
firebase projects:addfirebase sellersense-yinan920
firebase hosting:sites:create sellersense-ai
firebase deploy --only hosting            # rewrites ** → Cloud Run, config in firebase.json
```

Because the rewrite is `**` → Cloud Run, the single-container design is untouched: no build flag, no CORS, no code change, and the Cloud Run URL keeps working as the origin.

**Verification.** `https://sellersense-ai.web.app` serves the app; the E2E suites and the post-deployment smoke test run green against it. Playbook: [§1.4 I-6](01-production-support.md#i-6--the-public-short-url-is-down-but-the-app-is-up).

### Issue 8 — Batched sentiment scoring silently returned 183 results for 200 reviews

**What happened.** With `LLM_PROVIDER=anthropic`, a 200-review upload failed. *Expected:* 200 sentiment scores in review order. *Actual:* 183 results for 200 reviews, and a failed job. At 50 reviews the same code was exact — which is why the bug survived until dataset sizes grew.

**Environment.** Deployed service with real Claude (`claude-haiku-4-5` for sentiment), 200-row CSV (the premium tier cap).

**Reproduce.** Ask for one structured result per review for 200 reviews in a single request.

**Diagnosis.** A single request covering the whole dataset is unreliable at that length: the model returns fewer items than asked for, and a long structured response also risks running into `max_tokens`. The application had no arity check, so the mismatch propagated instead of failing loudly.

**Research.** Anthropic documentation on structured outputs / JSON schema and on `max_tokens` behaviour; the general batching guidance that smaller requests are more reliable than one large one.

**Resolution.** Chunk the work and verify arity ([`backend/app/integrations/llm/anthropic.py`](../backend/app/integrations/llm/anthropic.py)):

- 25 reviews per request (`SENTIMENT_BATCH`)
- 4 requests in flight (`SENTIMENT_CONCURRENCY`, via an `asyncio.Semaphore`)
- each chunk **asserts** it received exactly as many results as it sent, raising otherwise
- one automatic retry per chunk before the job fails

**Verification.** `200/200` reviews scored on every run of three consecutive benchmark runs. The sentiment stage takes 4.72–6.71 s for 200 reviews; the sum of the individual chunk latencies would be 17.74–25.55 s serially, so measured concurrency gain is ≈3.7×, consistent with a concurrency of 4 ([benchmarks.md §1](benchmarks.md#1-local-200-reviews-real-claude)).

### Issue 9 — Every theme came back as the same mush at 150 reviews

**What happened.** After adding a 150-row TikTok Shop dataset, the dashboard became useless. *Expected:* distinct themes such as slow shipping, packaging damage, battery life. *Actual:* five near-identical themes along the lines of "great coffee, but slow shipping", **all** flagged as complaints.

**Environment.** Real Claude for cluster labelling; 150-review dataset; cluster count hard-capped at 5.

**Reproduce.** Analyse 150 reviews with `k = 5`.

**Diagnosis.** The cap of 5 was tuned when 50 reviews was the only dataset. At 150 reviews it puts roughly 30 mixed reviews in each cluster, so every cluster contains every topic — and a labeller shown a mixed cluster can only produce a mixed label. The clustering was wrong, and the labelling faithfully reported it.

**Research.** Standard heuristics for choosing *k* in k-means (the `sqrt(n/2)` rule of thumb); scikit-learn `KMeans` documentation for `n_init` and `random_state` determinism.

**Resolution.** Scale the cluster count with the dataset ([`backend/app/services/pipeline.py`](../backend/app/services/pipeline.py)):

```python
def _pick_k(n_reviews: int) -> int:
    if n_reviews < 8:
        return min(2, n_reviews)
    return min(8, max(3, round((n_reviews / 2) ** 0.5)))
```

The cap of 8 keeps the dashboard readable — it is a UI decision, not a modelling limit — and 50-row behaviour is unchanged (`k = 5` either way).

**Verification.** 150 rows now separate 6 complaint themes from 2 strengths. 200 rows give `k = 8`. The 50-row sample produces the same 5 clusters as before, so no regression on the demo path.

### Issue 10 — Competitors crashed to a blank page for a premium account with no data

**What happened.** A newly upgraded premium account clicking *Competitors* got a completely blank page. *Expected:* an empty state explaining what to do. *Actual:* a white screen and a React error in the console.

**Environment.** Deployed frontend, premium account with zero analysed datasets. Found by the upgrade-flow E2E run — **no unit test covered it**, because the mock fixtures always contained data.

**Reproduce.** Upgrade a fresh account and open `/app/competitors` before uploading anything.

**Diagnosis.** The page indexed `data[0]` on the comparison array to render a summary header. For an account with no dataset the API correctly returns `[]`, so the index returned `undefined` and dereferencing it threw during render, taking the whole route down.

**Research.** React error-boundary and rendering-error behaviour (an uncaught error in render unmounts the tree); React Query documentation on distinguishing loading, empty and error states.

**Resolution.** Handle the empty case explicitly before touching any element ([`frontend/src/pages/Competitors.tsx:37`](../frontend/src/pages/Competitors.tsx#L37)) and render guidance — "upload your reviews to compare" — instead. The same audit was applied to the other premium pages.

**Verification.** The upgrade-flow E2E now asserts this exact state: *"empty benchmarking state renders instead of breaking"*, passing on 2026-08-24. A backend test (`test_competitors_premium_without_dataset_empty`) pins the API side of the contract.

### Issue 11 — Alerts and Competitors served stale data for up to 60 seconds after an upload

**What happened.** After an analysis completed, the dashboard updated but Alerts and Competitors kept showing the previous dataset's results. *Expected:* every view reflects the new analysis. *Actual:* up to 60 seconds of stale content.

**Environment.** React Query with a 60-second stale time; deployed frontend.

**Reproduce.** Upload a dataset, wait for "Analysis complete", then open Alerts within a minute.

**Diagnosis.** On upload completion only the `datasets` and `dashboard` queries were invalidated. Alerts and competitors are *derived from the same pipeline run* but are separate query keys, so React Query kept serving them from cache until their own stale time expired.

**Research.** TanStack Query documentation on query invalidation and `staleTime` semantics.

**Resolution.** Invalidate everything belonging to the account when an analysis finishes — the completion of a pipeline run makes all derived views stale by definition ([`frontend/src/pages/Upload.tsx:81`](../frontend/src/pages/Upload.tsx#L81)):

```ts
queryClient.invalidateQueries();
```

Broad invalidation is correct here: the event is rare (once per analysis) and the alternative is enumerating derived keys, which silently breaks whenever a new derived view is added.

**Verification.** E2E suites navigate straight from a completed upload to Competitors and Alerts and assert freshly derived content; both pass.

### Issue 12 — The premium gate was clipped, so the upgrade button was unreachable

**What happened.** On Alerts and Reply Studio, a free user saw the premium gate card cut off — including the upgrade button. *Expected:* the full gate with a working call to action. *Actual:* a visually truncated card; the paywall had no exit.

**Environment.** Deployed frontend, free-tier account, 1440×900 viewport.

**Reproduce.** Sign in as a free user and open `/app/alerts`.

**Diagnosis.** The gate overlay is absolutely positioned over blurred content, so the container took its height from the blurred children behind it. For a free user those children are a *short* empty state, so the container was shorter than the overlay, and `overflow-hidden` clipped what stuck out. On Competitors it happened to look fine because the placeholder behind it was taller — which is why it was easy to miss.

**Research.** CSS documentation on absolutely positioned elements being removed from normal flow and therefore not contributing to parent height; the interaction with `overflow: hidden`.

**Resolution.** Give the gate container a minimum height floor so it can never be shorter than the overlay ([`frontend/src/components/ui/PremiumGate.tsx:32`](../frontend/src/components/ui/PremiumGate.tsx#L32)):

```tsx
<div className="relative min-h-[26rem] overflow-hidden rounded-3xl">
```

**Verification.** The premium gate renders complete on the current deployment ([screenshot](images/guide/10-premium-gate.png)), and the upgrade-flow E2E captures the same for Alerts and Reply Studio (`frontend/e2e/shots-upgrade/06-gate-alerts.png` and `07-gate-reply.png` — E2E artifacts are written locally and not committed).

### Issue 13 — Instructor feedback: the paid tier was advertised but not functional

**What happened.** Feedback on the first presentation:

> *"The homepage also presents free and paid tiers, but the paid-tier functionality is not yet available; consider labeling that option 'Coming Soon' so the product experience accurately reflects the current implementation."*

The observation was correct at the time. The homepage advertised a $29 Premium plan, and the API enforced a real `402` on premium routes — but a free user who hit that wall **had no way forward**. There was no plans page, no purchase step, and no way to become premium except editing the database. The product promised something the implementation did not deliver.

**Environment.** State as presented: paywall enforcement implemented server-side; no upgrade path in the UI; `POST /billing/*` did not exist.

**Diagnosis.** Two honest options existed:

1. Label the paid tier "Coming Soon", making the marketing match the implementation; or
2. Implement the tier transition so the marketing becomes true.

Option 2 was chosen, because the missing piece was not the hard part. Tier gating, the caps, the premium features and the 402 responses were all already built and tested; what was missing was the *transition* between tiers — a few endpoints and two screens. Labelling it "Coming Soon" would have hidden a nearly complete feature.

**Research.** Stripe's documentation on hosted Checkout and on PCI DSS scope reduction (SAQ A), which is what makes a redirect-based payment design the right answer for a small application; the tier-based access patterns already used in the codebase.

**Resolution.** Implemented in two commits (`986a9b5`, `7223d7d`) — the paid tier is now functional end to end:

**Backend** — [`backend/app/api/billing.py`](../backend/app/api/billing.py):

| Endpoint | Behaviour |
|---|---|
| `GET /api/billing/plans` | Plan catalogue served from the API, so pricing and limits have one source of truth — the same caps the upload endpoint enforces |
| `POST /api/billing/upgrade` | Flips the account to Premium; 409 if already Premium; 401 without a token |
| `POST /api/billing/downgrade` | Returns to Free — the transition is demonstrable in both directions |

**Frontend** — two new routes:

- `/app/upgrade` — plan comparison, reachable from the premium gate and from the "Free plan" chip in the top bar, so the paywall always has an exit. The home page's own **"Go Premium"** button now routes here too, so the advertised tier leads to the actual purchase flow: a signed-out visitor is sent through sign-in or registration and then arrives at the plans page, rather than being dropped on the dashboard with their intent lost. *(That last part is committed but not yet deployed — it reaches the live site with the next `gcloud run deploy`.)*
- `/app/checkout` — order summary (plan, price, billing period, total) plus a payment-method chooser (card, PayPal, Apple Pay), then *Complete purchase*.

**The payment step is deliberately stubbed, and the page says so.** The checkout page **collects nothing**: it contains no card-number field, no CVV field — no data-collecting input elements at all. That is not laziness, it is the production design stated up front: a real deployment redirects to **Stripe Checkout**, so card data never reaches this server and the application stays out of PCI DSS scope. `upgrade()` is precisely where the Stripe webhook handler's logic would live. What *is* real is the part this application owns: the tier transition, and premium APIs unlocking immediately without re-login.

**Verification** (all executed 2026-08-24 against the live deployment):

| Evidence | Result |
|---|---|
| `test_billing.py` — 5 backend tests: catalogue mirrors the caps; upgrade unlocks premium routes with the same token; downgrade re-locks; double upgrade → 409; anonymous → 401 | ✅ |
| 6 frontend tests across `Upgrade.test.tsx` / `Checkout.test.tsx`, including one asserting the page has **no card number or CVV input anywhere** | ✅ |
| `upgrade-flow.mjs` — 11-assertion browser E2E covering chip → plans → checkout → purchase → premium unlocked → real competitor data, and asserting the checkout page contains **zero input elements** | ✅ |
| Post-deployment smoke S7 and S9 — upgrade unlocks premium routes with the *same* token; downgrade re-locks them | ✅ |
| Manual passes M-06 → M-09 with screenshots | ✅ |
| Browser check of the homepage entry point (2026-08-25): signed-out *Go Premium* → sign-in → plans page; new registration keeps the same destination; a plain sign-in with no intent still lands on the dashboard | ✅ |

![The plans page a free user reaches from the paywall](images/guide/11-upgrade-plans.png)

![Checkout — an order summary that collects no payment data by design](images/guide/12-checkout.png)

**Outcome.** The homepage's paid tier is **no longer aspirational**, so the "Coming Soon" label is not needed and has not been added: a visitor can register, hit the paywall, follow it to the plans page, review an order, complete the purchase, and use every premium feature — all self-serve, in under a minute. What remains simulated is payment capture alone, and the UI states that plainly rather than implying otherwise. The known-limitations list in [§4](04-user-guide.md#48-known-limitations--gotchas) says the same thing to end users.

### Issue 14 — E2E suite broke when production switched from mock adapters to real Claude

**What happened.** While re-running every test for this documentation (2026-08-24), the acceptance E2E suite failed against the deployed service. *Expected:* the 8-step suite passes as it did in August. *Actual:* it timed out at step 3 waiting for "Analysis complete".

**Environment.** Deployed revision `sellersense-00012-h2w` running `LLM_PROVIDER=anthropic` (the service was switched to real Claude and left there); Playwright/Chromium against `https://sellersense-ai.web.app`.

**Reproduce.** `BASE=https://sellersense-ai.web.app node e2e/acceptance.mjs` against a deployment running real Claude.

**Diagnosis.** Two independent assumptions in the test suite were true only for the deterministic adapters:

1. **Timing.** The step allowed 30 s for an analysis — generous when the mock pipeline finishes in about 2 s, insufficient now that the real pipeline takes ~20 s warm and ~34–40 s including a cold start (measured: 34 s in this session's smoke run).
2. **Exact strings.** Two assertions waited for the literal text `"Packaging damage"` — the mock labeller's fixed output. Real Claude writes the label itself, producing e.g. `"Damaged Packaging & Shipping Issues"`. The theme was found correctly; the assertion was simply too specific to survive a model-written label.

The underlying lesson: deterministic adapters make a run reproducible *within* an environment, and it is tempting to encode that determinism into assertions. Any test that must pass against both providers has to assert **structure and topic**, not exact strings and mock-era latencies.

**Research.** Playwright documentation on timeouts (`setDefaultTimeout` vs per-call `timeout`) and on resilient text matching; the project's own measured pipeline latencies in [benchmarks.md](benchmarks.md).

**Resolution.** In [`frontend/e2e/acceptance.mjs`](../frontend/e2e/acceptance.mjs):

```js
// Generous: with LLM_PROVIDER=anthropic a 50-review analysis takes ~20 s warm
// and ~40 s including a cold start, versus ~2 s on the deterministic adapters.
await page.getByText(/analysis complete/i).waitFor({ timeout: 180_000 });

// Match on the topic, not an exact label: with real Claude the theme name is
// model-written ("Damaged Packaging & Shipping Issues"), while the mock
// adapter always returns the fixed string "Packaging damage".
await page.getByText(/packaging/i).first().waitFor();
```

The alerts assertion was relaxed the same way, and its timeout raised from 20 s to 30 s.

**Verification.** All three browser suites now pass against the live deployment: acceptance (8 steps), upgrade-flow (11 assertions), delete-flow (5 assertions) — results in [§1.6.3](01-production-support.md#163-end-to-end-browser-tests-playwright--3-suites-passed).

**A second finding from the same session, recorded rather than hidden.** The investigation also caught stale documentation: the project README described the deployed demo as running the deterministic mock adapters, which stopped being true when the service was switched to real Claude and left there. Every public upload is therefore a metered API call. The README was corrected on 2026-08-25 to state the deployed configuration, to give the command for switching in either direction, and to name the two consequences of running the real path in public; the trade-off is described in [§5.4](05-architecture.md#54-ai-provider-strategy-and-the-current-production-setting).

### Issue 15 — The unit test suite could be silently pointed at a live backend

**What happened.** A developer with a `frontend/.env.local` containing `VITE_USE_MOCKS=false` (the normal setting for integrated development) would have Vitest pick that file up, so "unit" tests would issue real network calls.

**Environment.** Vite/Vitest, which loads `.env.local` for the current mode by default.

**Reproduce.** Set `VITE_USE_MOCKS=false` in `frontend/.env.local` and run `npm test` before the fix.

**Diagnosis.** Not a failure that announces itself: the suite would either pass slowly against real data or fail for reasons unrelated to the code under test, and the result would differ per developer machine. Test determinism must not depend on an untracked local file.

**Research.** Vite documentation on `.env` file precedence and modes; Vitest configuration reference for `test.env`.

**Resolution.** Pin the value in [`frontend/vite.config.ts`](../frontend/vite.config.ts) so the suite is deterministic regardless of local files; the API-contract tests that genuinely need real mode opt back out per file with `vi.stubEnv`:

```ts
test: {
  environment: 'jsdom',
  setupFiles: ['./src/test/setup.ts'],
  globals: true,
  env: { VITE_USE_MOCKS: 'true' },
}
```

**Verification.** `npm test` returns 20 passed on a machine with `VITE_USE_MOCKS=false` in `.env.local`, and the API tests still exercise real-mode request shapes.

### Issue 16 — A hidden 10-second cost on the first upload after a cold start

**What happened.** Benchmarking the deployed service showed the first `POST /datasets/upload` after an idle period taking **9.94 s**, even though `GET /api/health` had already warmed the container a moment earlier. *Expected:* ~0.1 s, since the upload endpoint only parses the CSV and inserts rows. *Actual:* ten seconds, once per container.

**Environment.** Cloud Run revision `sellersense-00012-h2w`, measured with `backend/scripts/bench_deployed.py`.

**Reproduce.** Let the service scale to zero, call `/api/health`, then upload and time the request.

**Diagnosis.** `BackgroundTasksRunner.enqueue` imports `app.workers.tasks` **inside the method** ([`backend/app/workers/runner.py`](../backend/app/workers/runner.py)), which transitively imports NumPy and scikit-learn. That import cost — several seconds — is therefore paid inside the first upload request rather than at container start. Production data confirmed it from the other side: one historical job shows a **10.21 s** gap between the job row being created and the pipeline starting.

**Research.** Python import-time cost of the scientific stack; Cloud Run documentation on startup CPU boost and container lifecycle; the project's own instrumentation in `scripts/bench_deployed.py`.

**Resolution and status.** Measured, documented, **not yet changed** — deliberately. The lazy import exists so that the module graph stays decoupled behind the `JobRunner` abstraction, and at demo traffic a one-off 10 s cost on the first upload per container is acceptable. The fix, when it matters, is to warm the import at application start (import `app.workers.tasks` once during startup, or set `--min-instances 1`), trading idle cost for latency.

**Verification.** The figure is reproducible: cold end-to-end ~39 s (≈9 s container start + ≈10 s import + ≈29 s analysis) versus 19–21 s warm, across four runs recorded in [benchmarks.md §2](benchmarks.md#2-deployed-50-reviews-real-claude). It also corrected an over-optimistic statement elsewhere in the documentation: cold start is ~9 s, not "a few seconds".
